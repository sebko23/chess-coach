## FU-4 — Whether to establish an `openapi-typescript` codegen pipeline at all (architectural)

**Identified:** FU-2 BBF (`doc-fix-pv-moves-uci-schema`) investigation, 2026-08-04.

**The question:**

- The frontend at `apps/desktop/src/services/coach/api.ts` is documented as auto-generated
  from the backend's FastAPI OpenAPI schema by `openapi-typescript`.
- The `openapi-typescript` CLI is NOT installed in this project:
  - Not in `apps/desktop/package.json` (deps or devDeps).
  - Not in `apps/desktop/node_modules/.bin/`.
  - Not in PATH.
  - Not in any venv.
- The file has been regenerated exactly ONCE in the project's history
  (`git log --all -- apps/desktop/src/services/coach/api.ts` shows one commit ever: `cd43906`,
  BBF-22, 2026-05-18-ish).
- No codegen script exists in `apps/desktop/package.json`, no Makefile, no `scripts/` entry,
  no CI step that runs codegen.

**Architectural decision needed (Sebastian+Claude directive 2026-08-04):**

> "Whether to establish an `openapi-typescript` codegen pipeline at all — a real
> architectural question (is frontend type drift from the backend schema something this
> project wants to prevent going forward, or is the frontend intentionally hand-maintained)
> — separate from any single fix, needs your input next session rather than being decided
> as a side effect of FU-2."

**Decision options:**

- (a) **Establish a codegen pipeline**: install `openapi-typescript` as a devDep in
  `apps/desktop/package.json`, add an npm script (e.g., `pnpm gen:api`) that runs the
  codegen against the backend's OpenAPI schema, document the workflow in `CONTRIBUTING.md`,
  enforce in CI via a "frontend types are up-to-date" check. Pros: future schema changes
  propagate automatically; frontend types stay in sync. Cons: new dependency + new build
  step; new CI surface to maintain.

- (b) **Accept hand-maintained frontend types**: treat `api.ts` as effectively
  hand-maintained despite the "auto-generated" header. Remove the header disclaimer or
  document the hand-maintained status. Pros: no new tooling. Cons: drift accumulates;
  future contributors may try to run the (non-existent) codegen and get confused.

- (c) **Defer**: leave the current state (no codegen, stale `api.ts`). The drift is
  currently cosmetic only (per FU-3). Pros: no immediate work. Cons: drift may become
  functional over time as the backend evolves.

**Status:** **RESOLVED 2026-08-04** by Sebastian+Claude directive: stand up codegen
scoped down from full proposal. Implemented 2026-08-05 as BBF-FU-4 (PR TBD).
Components (A)/(B)/(C)/(E)/(F) shipped; (D2) pre-commit hook skipped per directive.

## FU-5 — UCI→SAN conversion at the narration route boundary (UX gap)

**Identified:** FU-2 BBF investigation, 2026-08-04 (per Sebastian+Claude directive).

## FU-7 — Polyglot `.bin` opening-book import/export (low-priority feature gap)

**Identified:** Masterboard design-reference brief, 2026-08-06, during a
side-quest analysis of `https://github.com/IntermezzoSoftware/Masterboard`.
Brief: `docs/16_audit/MASTERBOARD-DESIGN-REFERENCE-BRIEF.md`.

**The gap:**

- chess-coach's repertoire system (per `services/chess_coach/gateway/routes/repertoire_recommendations.py`,
  post-BBF-87.2) has no support for importing or exporting opening books
  from external book formats.
- Masterboard supports Polyglot `.bin` books (a publicly documented format
  used by many chess apps for decades — Chessbase, Arena, Scid, etc.).
  Format spec is public; reimplementation from the spec is fine (not
  derivative work of any specific implementation).
- This would let users bring their existing opening repertoires from other
  tools into chess-coach and export chess-coach-built repertoires to
  other tools.

**Why low priority:**

- The protocol-defined Phase 1 surface does not include repertoire
  import/export (Phase 1 is engine analysis + grounded narration + game
  storage + position queries + opening explorer + jobs + health, per
  `specs/v1.0/chess-coach-protocol-v1.md:24`).
- Polyglot `.bin` import/export is a Phase 3-style feature, contingent
  on repertoire becoming a Phase 3 priority at all.
- No user has reported needing this; surfaced only as design-reference.

**Design references:**

- Polyglot book format spec: publicly documented (no single canonical
  doc, but the format is well-known — `magic number 0xB19B0BCC` + 8-byte
  entries with key = (position hash, move, weight, learn) at
  `big-endian uint64`).
- Masterboard implementation at `https://github.com/IntermezzoSoftware/Masterboard`
  is reference-only — GPL-3.0 vs chess-coach's MIT blocks direct code
  porting.

**Status:** OPEN. Low priority. Not blocking. Pick up only if/when
repertoire becomes a Phase 3 priority.

## FU-8 — Dead-code narration-context plumbing in `explain_simple()` (safe by accident, fragile)

**Identified:** FU-2 investigation, 2026-08-06, during the
injection-pattern / tool-fabrication investigation.
Investigation brief:
`C:\Users\i3\AppData\Local\hermes\cache\hermes\hermes-agent\chess-coach\FU-2-injection-tool-fabrication-investigation.md`.

**The gap:**

The route handler at
`services/chess_coach/gateway/routes/narration.py:128-149` builds
`prompt_context` from `body.move_san`, `body.eval_cp`, `body.game_phase`,
and `body.context` (with the A-F12 `sanitize_user_content()` call on
the `context` field at line 144-146). It passes this string to
`pipeline.explain_simple(..., context=prompt_context)` at line 250
(synthetic path only).

`pipeline.explain_simple` (signature at
`services/chess_coach/narration/pipeline.py:320-326`) accepts
`fen`, `move_san`, `eval_cp`, `game_phase`, `context` as parameters.
**The `context` parameter is never referenced in the function body.**
**`move_san` and `game_phase` are also accepted and never used.**
Only `eval_cp` is consumed (to construct the synthetic `AnalysisResult.score`).

`pipeline.explain` then calls `build_user_prompt(result, grounding_block=...)`
at `narration/prompt.py:46-62`. The `build_user_prompt` signature
**does not include a `context` parameter.** The user prompt is the
optional grounding block + the engine analysis (FEN + PV lines +
depth/engine-id).

**Net effect:** user-controlled fields `move_san`, `eval_cp`,
`game_phase`, `context` are **collected and sanitized at the route
but silently dropped before reaching the LLM prompt.** The only
user-controlled string the LLM sees is the `fen` field, which is
constrained to a parseable chess position by
`NarrationRequest.validate_fen` (pydantic validator using
`chess.Board(v)`).

**Why this is "safe by accident, not by design":**

- The A-F12 sanitization at
  `services/chess_coach/narration/sanitize.py:174-235` IS correctly
  applied to `body.context` at the route boundary (line 144-146 of
  `narration.py`).
- The sanitized string is **not currently plumbed into the LLM
  prompt at any point.**
- The system prompt's UNTRUSTED CONTENT section
  (`prompt.py:19-28`) is in place to defend against
  `<user_content>`-wrapped text — but no such text is currently
  produced by the code path.

**This is safe today** (the LLM only sees the engine analysis
and FEN), but the safety is **incidental, not designed**. The
plumbing (route → `explain_simple` signature → would-be prompt)
is real, and a future change to complete the dead-code path
(wire `prompt_context` into `build_user_prompt`) would create
the injection surface that the A-F12 sanitizer is currently
sitting unused as the gatekeeper for.

**Why this is fragile:**

- The sanitizer module has its own docstring
  (`sanitize.py:1-55`) describing the A-F12 mitigations as if
  they're actively protecting the prompt. They're plumbed
  correctly, but they're defending against a path that doesn't
  exist.
- A future BBF (e.g., "complete the narration context wiring" as
  suggested by FU-2 Finding 5) would need to:
  1. Extend `build_user_prompt` to accept a `user_context` parameter
     that wraps the sanitized string in `<user_content>` delimiters
     (the current `sanitize_user_content` does this wrapping
     already, so the wire-up is straightforward).
  2. Add a `user_context` parameter to `pipeline.explain` and
     `pipeline.explain_simple`.
  3. Re-test the system prompt's UNTRUSTED CONTENT section
     against the now-active `<user_content>` block.
  4. Add a `move_san` and `game_phase` plumbing if those
     fields are to be threaded through too.
- Without this note, a future engineer might:
  - Notice the dead code and "clean it up" by removing the
    `context=` parameter entirely, deleting the
    `sanitize_user_content` call from the route handler, and
    removing the UNTRUSTED CONTENT section from the system
    prompt as "unused."
  - This would be correct cleanup, but it would also remove
    the standing defense-in-depth that is currently
    accidentally protecting the prompt.
  - **OR** alternatively, the engineer might complete the
    wiring without realizing the A-F12 sanitizer is intended
    to be the gatekeeper, accidentally introducing an
    injection surface.

**Recommendation: log this and leave it as-is for now.** No
implementation work is authorized in this follow-up entry.
The current state is safe; the next engineer to touch this
code path should be made aware that the dead plumbing is
intentional defense-in-depth, not leftover refactor cruft.

**Related code locations** (all verified by direct read of
the chess-coach source as of commit `cada4ab2` on
`origin/main`, 2026-08-06):

- Route handler: `services/chess_coach/gateway/routes/narration.py:128-149, 250`
- Pipeline signature: `services/chess_coach/narration/pipeline.py:320-326`
- Pipeline body: `services/chess_coach/narration/pipeline.py:339-374`
  (the synthetic `AnalysisResult` is built from `fen` + `eval_cp`
  only; `move_san`, `game_phase`, `context` are not stored on
  the result)
- Prompt construction: `services/chess_coach/narration/prompt.py:46-62`
  (`build_user_prompt` signature is `(result, *, grounding_block="")`)
- System prompt UNTRUSTED CONTENT section:

## FU-17 — Pin pnpm version durably via `packageManager` + corepack (structural fix for FU-13)

**Identified:** 2026-08-09, when FU-13's threshold tracker reached
3/3 instances and the third instance (the pnpm-version drift in
PR #86) was a recurrence of the same problem that had been patched
around once already during FU-4.

**Why this is a separate item from FU-14:**

FU-14 patches around the immediate failure (the `pnpm-workspace.yaml`
overrides block produces a lockfile that CI's pnpm 10.34.5 rejects
when generated under local pnpm 11.1.2). FU-17 prevents the pattern
from recurring by durably pinning the project's pnpm version so local
and CI always use the same version.

**The underlying cause of the pattern:**

The repo has no `packageManager` field in `package.json` and no
corepack setup. This means each developer's local machine uses
whatever pnpm happens to be globally installed (in this project's
case, the Hermes-agent's bundled pnpm 11.1.2), and CI uses whatever
version its `pnpm/action-setup@v4` is configured to (10.34.5). When
those versions produce different lockfile signatures — which they
do, because pnpm 10 and pnpm 11 have lockfile format differences —
the developer's local `pnpm install` produces a lockfile CI rejects,
and the cycle repeats.

**Suggested fix approach (not implemented in this turn; planned
for a future BBF):**

1. Add `"packageManager": "pnpm@10.34.5"` to `apps/desktop/package.json`
   (top-level field, not inside `dependencies`).
2. Add a `packageManager` field to the workspace root `package.json`
   too if applicable (the chess-coach project is a workspace with
   `apps/desktop` as a subproject).
3. Enable corepack via `corepack enable pnpm@10.34.5` (or rely on
   the `packageManager` field's automatic corepack shimming).
4. Update CI's `pnpm/action-setup@v4` step to align with the pinned
   version (currently pnpm 10; check that 10.34.5 specifically is
   what the action installs by default, or pin to `version: 10.34.5`
   in the workflow YAML).
5. Regenerate the lockfile under the pinned version and commit.
6. Verify CI's `pnpm install --frozen-lockfile` step passes without
   the config-mismatch error.

**Status:** OPEN. Moderate priority. Same threshold-3-driven urgency
as the other FU-13-promoted structural fixes. Not blocking the FU-14
PR merge (FU-14's path-1 patch-around is the correct contained fix
for the immediate failure), but should be addressed before the next
JS-dep-related BBF to avoid the next patch-around.
