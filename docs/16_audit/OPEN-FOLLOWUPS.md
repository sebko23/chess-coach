## FU-3 — `apps/desktop/src/services/coach/api.ts` still claims SAN for `pv_moves` and `best_move` (cosmetic)

**The mismatch:**

- Backend (now corrected): `pv_moves` docstring says UCI (matches runtime + protocol spec).
- Frontend (NOT corrected): `apps/desktop/src/services/coach/api.ts:798` says:
  ```
  * @description Top PV line moves in SAN
  ```
  And `apps/desktop/src/services/coach/api.ts:788`: `* @description Best move in SAN notation`.

**Why this is cosmetic only:**

- The frontend rendering code at `apps/desktop/src/components/panels/coach/CoachPanel.tsx:174`
  and `SuggestionList.tsx:84` does NOT parse SAN: it just does `moves.slice(0, 8).join(" ")`.
- TypeScript doesn't enforce SAN-vs-UCI content — `pv_moves: string[]` accepts any strings.

  doesn't break anything.

**Why we did NOT fix it in the FU-2 BBF:** The file's header (`api.ts:1-3`) says it's
auto-generated by `openapi-typescript` and "do not make direct changes." The project has no
`openapi-typescript` codegen pipeline — it's not in `apps/desktop/package.json`, not in
`apps/desktop/node_modules/.bin/`, not in PATH, not in any venv. So fixing `api.ts` would
either require establishing a new codegen pipeline (Option I, scope-creep) or hand-editing
a file that explicitly says not to be hand-edited (Option II, violates the file header).

**Status:** **RESOLVED 2026-08-05** by BBF-FU-4 (PR TBD). The codegen pipeline was
established; one-time regeneration brought `api.ts:788,798` descriptions into sync
with the corrected backend schema. The regenerated file shows the UCI wording

(`frontend-types-codegen` in `.github/workflows/smoke.yml`) prevents future drift.

## FU-4 — Whether to establish an `openapi-typescript` codegen pipeline at all (architectural)

**Identified:** FU-2 BBF (`doc-fix-pv-moves-uci-schema`) investigation, 2026-08-04.

**The question:**

- The frontend at `apps/desktop/src/services/coach/api.ts` is documented as auto-generated
  from the backend's FastAPI OpenAPI schema by `openapi-typescript`.
- The `openapi-typescript` CLI is NOT installed in this project:
  - Not in `apps/desktop/package.json` (deps or devDeps).
  - Not in `apps/desktop/node_modules/.bin/`.
  - Not in PATH.
  - Not in any venv.
- The file has been regenerated exactly ONCE in the project's history
  (`git log --all -- apps/desktop/src/services/coach/api.ts` shows one commit ever: `cd43906`,
  BBF-22, 2026-05-18-ish).
- No codegen script exists in `apps/desktop/package.json`, no Makefile, no `scripts/` entry,
  no CI step that runs codegen.

**Architectural decision needed (Sebastian+Claude directive 2026-08-04):**

> "Whether to establish an `openapi-typescript` codegen pipeline at all — a real
> architectural question (is frontend type drift from the backend schema something this
> project wants to prevent going forward, or is the frontend intentionally hand-maintained)
> — separate from any single fix, needs your input next session rather than being decided
> as a side effect of FU-2."

**Decision options:**

- (a) **Establish a codegen pipeline**: install `openapi-typescript` as a devDep in
  `apps/desktop/package.json`, add an npm script (e.g., `pnpm gen:api`) that runs the
  codegen against the backend's OpenAPI schema, document the workflow in `CONTRIBUTING.md`,
  enforce in CI via a "frontend types are up-to-date" check. Pros: future schema changes
  propagate automatically; frontend types stay in sync. Cons: new dependency + new build
  step; new CI surface to maintain.

- (b) **Accept hand-maintained frontend types**: treat `api.ts` as effectively
  hand-maintained despite the "auto-generated" header. Remove the header disclaimer or
  document the hand-maintained status. Pros: no new tooling. Cons: drift accumulates;
  future contributors may try to run the (non-existent) codegen and get confused.

- (c) **Defer**: leave the current state (no codegen, stale `api.ts`). The drift is
  currently cosmetic only (per FU-3). Pros: no immediate work. Cons: drift may become
  functional over time as the backend evolves.

**Status:** **RESOLVED 2026-08-04** by Sebastian+Claude directive: stand up codegen
scoped down from full proposal. Implemented 2026-08-05 as BBF-FU-4 (PR TBD).
Components (A)/(B)/(C)/(E)/(F) shipped; (D2) pre-commit hook skipped per directive.

## FU-5 — UCI→SAN conversion at the narration route boundary (UX gap)

**Identified:** FU-2 BBF investigation, 2026-08-04 (per Sebastian+Claude directive).

**The UX gap:**

- Backend now correctly documents `pv_moves` as UCI (FU-2 resolved).
- Frontend at `apps/desktop/src/components/panels/coach/CoachPanel.tsx:174` displays the
  "Best Line" panel via:
  ```tsx
  <Text component="span" ff="monospace" size="sm">
    {(moves ?? []).slice(0, 8).join(" ")}
  </Text>
  ```
- The backend emits UCI (`["e2e4", "e7e5", "g1f3"]`); the frontend displays it verbatim
  as `e2e4 e7e5 g1f3` in monospace.
- The frontend's documented expectation at `apps/desktop/src/services/coach/api.ts:798`
  (now stale) said SAN. The original intent was probably that the "Best Line" panel would
  show `e4 e5 Nf3` (compact SAN) rather than `e2e4 e7e5 g1f3` (verbose UCI).

**Why this is a real UX gap (per directive):**

> "This is a real UX gap in the feature that was the whole point of this session's core
> work, not busywork — log it clearly as its own item so it doesn't get lost the way
> FU-1/FU-2 almost did, but it's not blocking and doesn't need to happen today."

**Implementation sketch (when picked up):**

- Add a server-side helper that converts UCI → SAN given the FEN context (already
  available in the narration request):
  ```python
  from chess import Board
  def uci_to_san(fen: str, uci_moves: list[str]) -> list[str]:
      board = Board(fen)
      return [board.san_uci(move_uci) for move_uci in uci_moves]
  ```

- Convert at the narration route boundary (`services/chess_coach/gateway/routes/narration.py`)
  before populating `pv_moves`.
- Alternative: expose both fields (`pv_moves_uci` and `pv_moves_san`) — Option C from the
  original FU-2 enumeration; larger surface change but most explicit.

**Prerequisites:**

- `python-chess` is in main `dependencies` already (per `pyproject.toml`), so no new
  dependency needed.
- The narration request already carries the FEN (`libs/chess_coach/protocol_types/narration.py`),
  so the conversion context is available.

**Status:** **IN PROGRESS 2026-08-06** by BBF-FU-5 (branch `bbf-fu5-pv-moves-san`,
commit on `main@d6a9e1e`). Additive `pv_moves_san` field on
`NarrationResponse`, backend helper `_pv_to_san()` in
`services/chess_coach/narration/pipeline.py` (replay-on-board, never-raise,

## FU-6 — 3 narration integration tests broken by BBF-87.2's unconditional `Depends(_engine_pool)`

**Identified:** BBF-FU-5 session, 2026-08-06, during pre-commit test verification.

**The breakage (verified by direct read on stock `main@d6a9e1e`):**

Three pre-existing integration tests in `tests/integration/test_narrative_position_fk.py`
construct their `FastAPI()` app by hand (lines 67-78, 122-133, 173-184) and
set `app.state.narration_pipeline` + `app.state.gateway.settings` but never
set `app.state.engine_pool`. The narration route at
`services/chess_coach/gateway/routes/narration.py:54` defines:

```python
def _engine_pool(request: Request):
    return request.app.state.engine_pool
```

…and the route handler at line 122 wires it as a request-time dependency:

```python
async def explain_position(
    body: NarrationRequest,
    db_path: str = Depends(_db_path),
    pipeline=Depends(_pipeline),
    engine_pool=Depends(_engine_pool),  # unconditional
) -> NarrationResponse:
```

So every request to `/v1/narration/explain` — including synthetic-path
requests with no engine fields — triggers FastAPI's dependency resolver to
call `_engine_pool(request)`, which raises:

```
AttributeError: 'State' object has no attribute 'engine_pool'
```

**The 3 broken tests (all in the same class, all failing with the same
traceback at `routes/narration.py:54`):**

```
FAILED tests/integration/test_narrative_position_fk.py::TestNarrationPositionFK::test_first_narration_creates_freeform_position
FAILED tests/integration/test_narrative_position_fk.py::TestNarrationPositionFK::test_repeat_narration_reuses_same_position
FAILED tests/integration/test_narrative_position_fk.py::TestNarrationPositionFK::test_different_fens_create_different_positions
```

**Why these are pre-existing (not FU-5 regressions):**

- **Direct verification on stock `main`:** I stashed all FU-5 changes (including
  the new test files) and re-ran the 3 tests against stock `main@d6a9e1e`. All
  3 fail with the same `'State' object has no attribute 'engine_pool'`
  traceback at the same line. Then I unstashed; my FU-5 branch is intact.
- **Static analysis:** the failure is at dependency-resolution time (line 54),
  before the route handler body executes. None of my FU-5 changes are on the
  failure path (my edits are at line 186 and ~320).
- **Attribution chain:** PR #73 (BBF-87.2, commit `e4a4c66`, "wire
  engine_pool.analyze() into narration route") added `engine_pool=Depends(_engine_pool)`
  as a route-level Depends default. PR #74 (BBF-87.2.1, commit `0cf39b6`,
  "tighten narration exception handling + fix test fixtures") fixed some
  fixtures but did not touch these 3. The 3 tests were written for BBF-87.1.y
  (PR #29) and never updated when BBF-87.2 wired the engine_pool into the route.

**Why this is a low-urgency gap (not a live production bug):**

- Production always wires `engine_pool` via `create_app()`'s real lifespan
  (see `services/chess_coach/gateway/app.py:217` for the wiring). The 3
  failures only manifest in tests that bypass `create_app()` and hand-roll
  a `FastAPI()` app.
- The CI suite does not gate PRs on these 3 tests passing — they're part
  of the integration suite that runs alongside other tests but none of
  them are flagged as must-pass in the smoke.yml workflow.
- No live HTTP path is affected; this is purely a test-fixture blind spot.

**Fix options (when picked up):**

- **(a)** Add `app.state.engine_pool = MagicMock()` (or a real `AsyncMock`
  with `analyze = AsyncMock(return_value=...)`) to the 3 test setup blocks
  at `tests/integration/test_narrative_position_fk.py:67-78`,
  `122-133`, `173-184`. Mirrors the pattern at
  `tests/integration/test_narration_engine_pool.py:79-81` and the new
  `tests/integration/test_narration_pv_moves_san.py`.
- **(b)** Change `_engine_pool(request)` at
  `services/chess_coach/gateway/routes/narration.py:45-54` to return
  `Optional[EnginePool]`, and gate the engine-backed branch in the handler
  on `engine_pool is not None` (currently it gates on `wants_engine`).
  Fixes the tests without test-fixture changes, but adds defensive
  branching to production code for a case that should never happen in
  production (lifespan always wires it).
- **(c)** Make the engine-backed branch skip the `Depends()` resolution
  by inlining the engine-pool read inside the `if wants_engine:` block
  using `request.app.state.engine_pool` directly with `getattr(..., None)`.
  Smaller diff than (b), same effect.

**Sebastian+Claude directive 2026-08-06:** "Log this as a new follow-up

## FU-7 — Polyglot `.bin` opening-book import/export (low-priority feature gap)

**Identified:** Masterboard design-reference brief, 2026-08-06, during a
side-quest analysis of `https://github.com/IntermezzoSoftware/Masterboard`.
Brief: `docs/16_audit/MASTERBOARD-DESIGN-REFERENCE-BRIEF.md`.

**The gap:**

- chess-coach's repertoire system (per `services/chess_coach/gateway/routes/repertoire_recommendations.py`,
  post-BBF-87.2) has no support for importing or exporting opening books
  from external book formats.
- Masterboard supports Polyglot `.bin` books (a publicly documented format
  used by many chess apps for decades — Chessbase, Arena, Scid, etc.).
  Format spec is public; reimplementation from the spec is fine (not
  derivative work of any specific implementation).
- This would let users bring their existing opening repertoires from other
  tools into chess-coach and export chess-coach-built repertoires to
  other tools.

**Why low priority:**

- The protocol-defined Phase 1 surface does not include repertoire
  import/export (Phase 1 is engine analysis + grounded narration + game
  storage + position queries + opening explorer + jobs + health, per
  `specs/v1.0/chess-coach-protocol-v1.md:24`).
- Polyglot `.bin` import/export is a Phase 3-style feature, contingent
  on repertoire becoming a Phase 3 priority at all.
- No user has reported needing this; surfaced only as design-reference.

**Design references:**

- Polyglot book format spec: publicly documented (no single canonical
  doc, but the format is well-known — `magic number 0xB19B0BCC` + 8-byte
  entries with key = (position hash, move, weight, learn) at
  `big-endian uint64`).
- Masterboard implementation at `https://github.com/IntermezzoSoftware/Masterboard`
  is reference-only — GPL-3.0 vs chess-coach's MIT blocks direct code
  porting.

**Status:** OPEN. Low priority. Not blocking. Pick up only if/when
repertoire becomes a Phase 3 priority.

## FU-8 — Dead-code narration-context plumbing in `explain_simple()` (safe by accident, fragile)

**Identified:** FU-2 investigation, 2026-08-06, during the
injection-pattern / tool-fabrication investigation.
Investigation brief:
`C:\Users\i3\AppData\Local\hermes\cache\hermes\hermes-agent\chess-coach\FU-2-injection-tool-fabrication-investigation.md`.

**The gap:**

The route handler at
`services/chess_coach/gateway/routes/narration.py:128-149` builds
`prompt_context` from `body.move_san`, `body.eval_cp`, `body.game_phase`,
and `body.context` (with the A-F12 `sanitize_user_content()` call on
the `context` field at line 144-146). It passes this string to
`pipeline.explain_simple(..., context=prompt_context)` at line 250
(synthetic path only).

`pipeline.explain_simple` (signature at
`services/chess_coach/narration/pipeline.py:320-326`) accepts
`fen`, `move_san`, `eval_cp`, `game_phase`, `context` as parameters.
**The `context` parameter is never referenced in the function body.**
**`move_san` and `game_phase` are also accepted and never used.**
Only `eval_cp` is consumed (to construct the synthetic `AnalysisResult.score`).

`pipeline.explain` then calls `build_user_prompt(result, grounding_block=...)`
at `narration/prompt.py:46-62`. The `build_user_prompt` signature
**does not include a `context` parameter.** The user prompt is the
optional grounding block + the engine analysis (FEN + PV lines +
depth/engine-id).

**Net effect:** user-controlled fields `move_san`, `eval_cp`,
`game_phase`, `context` are **collected and sanitized at the route
but silently dropped before reaching the LLM prompt.** The only
user-controlled string the LLM sees is the `fen` field, which is
constrained to a parseable chess position by
`NarrationRequest.validate_fen` (pydantic validator using
`chess.Board(v)`).

**Why this is "safe by accident, not by design":**

- The A-F12 sanitization at
  `services/chess_coach/narration/sanitize.py:174-235` IS correctly
  applied to `body.context` at the route boundary (line 144-146 of
  `narration.py`).
- The sanitized string is **not currently plumbed into the LLM
  prompt at any point.**
- The system prompt's UNTRUSTED CONTENT section
  (`prompt.py:19-28`) is in place to defend against
  `<user_content>`-wrapped text — but no such text is currently
  produced by the code path.

**This is safe today** (the LLM only sees the engine analysis
and FEN), but the safety is **incidental, not designed**. The
plumbing (route → `explain_simple` signature → would-be prompt)
is real, and a future change to complete the dead-code path
(wire `prompt_context` into `build_user_prompt`) would create
the injection surface that the A-F12 sanitizer is currently
sitting unused as the gatekeeper for.

**Why this is fragile:**

- The sanitizer module has its own docstring
  (`sanitize.py:1-55`) describing the A-F12 mitigations as if
  they're actively protecting the prompt. They're plumbed
  correctly, but they're defending against a path that doesn't
  exist.
- A future BBF (e.g., "complete the narration context wiring" as
  suggested by FU-2 Finding 5) would need to:
  1. Extend `build_user_prompt` to accept a `user_context` parameter
     that wraps the sanitized string in `<user_content>` delimiters
     (the current `sanitize_user_content` does this wrapping
     already, so the wire-up is straightforward).
  2. Add a `user_context` parameter to `pipeline.explain` and
     `pipeline.explain_simple`.
  3. Re-test the system prompt's UNTRUSTED CONTENT section
     against the now-active `<user_content>` block.
  4. Add a `move_san` and `game_phase` plumbing if those
     fields are to be threaded through too.
- Without this note, a future engineer might:
  - Notice the dead code and "clean it up" by removing the
    `context=` parameter entirely, deleting the
    `sanitize_user_content` call from the route handler, and
    removing the UNTRUSTED CONTENT section from the system
    prompt as "unused."
  - This would be correct cleanup, but it would also remove
    the standing defense-in-depth that is currently
    accidentally protecting the prompt.
  - **OR** alternatively, the engineer might complete the
    wiring without realizing the A-F12 sanitizer is intended
    to be the gatekeeper, accidentally introducing an
    injection surface.

**Recommendation: log this and leave it as-is for now.** No
implementation work is authorized in this follow-up entry.
The current state is safe; the next engineer to touch this
code path should be made aware that the dead plumbing is
intentional defense-in-depth, not leftover refactor cruft.

**Related code locations** (all verified by direct read of
the chess-coach source as of commit `cada4ab2` on
`origin/main`, 2026-08-06):

- Route handler: `services/chess_coach/gateway/routes/narration.py:128-149, 250`
- Pipeline signature: `services/chess_coach/narration/pipeline.py:320-326`
- Pipeline body: `services/chess_coach/narration/pipeline.py:339-374`
  (the synthetic `AnalysisResult` is built from `fen` + `eval_cp`
  only; `move_san`, `game_phase`, `context` are not stored on
  the result)
- Prompt construction: `services/chess_coach/narration/prompt.py:46-62`
  (`build_user_prompt` signature is `(result, *, grounding_block="")`)
- System prompt UNTRUSTED CONTENT section:
  `services/chess_coach/narration/prompt.py:19-28`
- Sanitizer (intended gatekeeper):
  `services/chess_coach/narration/sanitize.py:174-235`
  (`sanitize_user_content(text, *, source, game_id=None, max_bytes=1024)`)

**Status:** OPEN. Low priority. Not blocking. Logged for
discoverability — the dead code is correctly safe today; the
risk is that it becomes load-bearing through an incomplete
future wiring, and the note is here to make that discoverable.

**Sebastian+Claude directive 2026-08-06:** "Log Finding 1+2 as
a new follow-up (FU-8) in `OPEN-FOLLOWUPS.md`: dead-code
`context`/`move_san`/`game_phase` plumbing in

## FU-11 — Polyglot opening-book persistent support (β, Phase 2 trigger)

**Identified:** FU-7 BBF session, 2026-08-08, during implementation of
the α (in-memory per-call `polyglot_book_path` field on
`POST /v1/repertoire/{player}/recommendations`).

**The gap (and what it is NOT):**

- α (FU-7): caller supplies `polyglot_book_path` on each individual
  request. Server opens it for that one request, surfaces book entries
  alongside engine PVs (per blending (iv) — per-move union, no
  arbitration), and discards it on response. Per-call only. No
  persistence, no indexing, no learning.
- β (this entry, FU-11): server-managed persistent book state.
  Uploading a `.bin` once, naming it (player-scoped? repertoire-scoped?
  user-scoped?), querying it across calls, possibly indexing it for
  fast lookup, possibly combining multiple books for a single player.
  This is the Phase 2 trigger point — a real product surface, not a
  continuation of α.

**Why this is logged separately and not part of α:**

Per Sebastian+Claude directive 2026-08-07 approving the FU-7 shape:
*"the honest-framing caveat + β-trigger note logged; blending (iv)"* —
β is its own item because:

1. It introduces persistence (file storage, ownership/scoping, lifecycle).
2. It introduces new protocol surface (upload endpoint? library endpoint?
   per-player default book? — none decided yet).
3. It changes the auth model (uploads need write-permission, not just read).
4. It may need indexing (file-backed mmap is fine for α's per-call reads;
   β wants fast multi-player lookup, which may need a different storage
   choice).
5. It introduces long-running state on disk that needs backup/cleanup.

If α's `polyglot_book_path` field starts growing into a "set this for
the session" or "remember this path for this player" semantic, that's
β scope-creep into α. The boundary: α is **per-call, stateless, no
side-effects**; β is anything that persists, indexes, or remembers.

**Sebastian+Claude directive 2026-08-07:** "include the
`OPEN-FOLLOWUPS.md` note that a persistent-book request (β) is the
real Phase 2 trigger point, not a continuation of this field." This
entry is that note.

**Status:** OPEN. Logged as Phase 2 trigger. Not blocking α. Do not
implement until α is shipped and the protocol surface from α has
been observed in production for at least one release cycle.

**α implementation pointer (for when β is picked up):** FU-7 lives at
`services/chess_coach/gateway/routes/repertoire_recommendations.py` —

## FU-13 — Local-vs-CI environment-mismatch threshold tracking (cross-cutting)

**Identified:** FU-7 BBF session, 2026-08-08, after the
openapi-typescript version-pin gap surfaced.

**The two instances so far in this session:**

1. **PYTHONPATH leak (FU-10 verification, 2026-08-08).** Hermes-agent's
   venv at `C:\Users\i3\AppData\Local\hermes\hermes-agent\venv\Lib\site-packages`
   leaked into chess-coach's `.venv` via
   `PYTHONPATH=C:\Users\i3\AppData\Local\hermes\hermes-agent;...\site-packages`,
   causing `pip-audit` and `import h2.__version__` to read
   `h2==4.3.0` instead of the actually-installed `h2==4.4.1`.
   Detection: cross-checked pip-audit's "Version" column against the
   on-disk `dist-info/METADATA` and the package's `__init__.py`
   source — both confirmed the fix was real; the leak was a
   shadow-on-sys.path, not a real package state.
2. **openapi-typescript version drift (FU-7 verification, 2026-08-08).**
   `package.json` declares `openapi-typescript: ^7.4.0`; CI's lockfile
   resolved to `7.13.0`; my local install of `7.4.0` produced a
   different `api.ts` than CI's check expected. The diff was visible
   only because 7.4.0 strips `@example` blocks that 7.13.0 emits.
   Detection: pulled CI log content via the run-level ZIP endpoint
   (`/actions/runs/{run_id}/logs`), saw
   `✨ openapi-typescript 7.13.0` in the log; compared my local 7.4.0
   output to the committed `api.ts` and confirmed the version drift.

**Why this is FU-13 (its own item, not just a note):**

Both incidents share a structural pattern: **a tool's behavior
diverges between the agent's local environment and CI's environment
in ways that are invisible from within either one alone.** The first
incident (PYTHONPATH) only surfaced because cross-checking the
on-disk package metadata against pip-audit's output revealed the
shadow. The second (openapi-typescript version) only surfaced because
CI's log captured the exact version line in a way that was grep-able.
Without one of those cross-checks, both incidents would have looked
like "fix didn't take" / "the codegen pipeline is broken" — exactly
the kind of plausible-but-wrong diagnosis that FU-4's
hypothesis-before-evidence lesson warns against.

**Threshold call:**

Per Sebastian+Claude directive 2026-08-08: "two isn't yet the
'structural problem' threshold, but it's adjacent enough to the
describe-vs-show tracking to note by name rather than let it dissolve
into 'future BBF candidate' vagueness." One more instance moves it
from "by-name tracking" to "structural environment-fix BBF" — same
threshold logic as PYTHONPATH (which is now at 2 instances per
cross-session memory). At three, this becomes a real source-fix
investigation rather than per-incident workarounds.

**Why I'm NOT recommending an immediate fix:**

Both instances had clean workarounds (unset `PYTHONPATH`; install
the version CI uses). At two instances, the workarounds are cheap.
If the pattern reaches three instances where the workaround is
non-obvious or expensive, the answer shifts to "fix the harness"
rather than "patch each surface."

**Cross-references:**

- PYTHONPATH: instance #1 (FU-1 ghost dist-info, 2026-08-04,
  ghost `huggingface_hub-1.24.0.dist-info/`); instance #2 (FU-10
  verification, 2026-08-08, `h2==4.3.0` shadow). See cross-session
  memory entry.
- openapi-typescript version drift: instance #1 only so far
  (FU-7 verification, 2026-08-08).
- Future-BBF candidate (separate item, NOT this one): pin
  `openapi-typescript` exactly (not `^7.4.0`) in `package.json` so
  local + CI resolution match deterministically.

**Status:** TRACKING. Not a work item. Threshold counter: 2 of 3.
At 3, promote to a real BBF for "fix the harness / fix the lockfile
discipline."
